# AUD-11 — Readiness implementasi backend koreksi absensi

**Status:** implementasi _gated_ menunggu keputusan owner AUD-10; analisis lokal AUD-11 selesai.  
**Tanggal analisis:** 15 Oktober 2026 (Asia/Jakarta).  
**Batas:** satu artefak analisis ini saja. Tidak mengubah kode, schema, migrasi, OpenAPI, database, atau Git state. Rekomendasi AUD-10 tetap opsi, bukan kebijakan yang disetujui.

## Kesimpulan

Belum aman mengaktifkan koreksi melalui request biasa. `RequestType.CORRECTION` dan model `AttendanceCorrection` memang sudah ada, tetapi service/route aktif menolak tipe tersebut; target koreksi belum terikat eksplisit ke satu shift dan tanggal; workflow persetujuan belum membuat status efektif dan audit dalam satu transaksi; serta pilihan approver, kalender H+3, klaim waktu, dan interaksi closing belum dikunci owner. Ada port repository parsial untuk menerapkan koreksi `CHECK_IN` ke projection `DailyAttendance`, bukan workflow koreksi lengkap.

Status implementasi gated tidak menghentikan artefak lokal ini. Matriks, peta perubahan, strategi transaksi, dan rencana uji di bawah dapat dipakai untuk melanjutkan segera setelah policy lock.

## Temuan source yang membatasi implementasi

- **Request yang aktif bukan correction.** `RequestType.CORRECTION` ada di enum, tetapi `EMPLOYEE_REQUEST_TYPES` di `apps/api/src/modules/attendance-requests/index.ts` hanya berisi LEAVE/SICK/ANNUAL_LEAVE/OVERTIME. Service memvalidasi ulang tipe tersebut. `apps/api/src/routes/attendance-requests.ts` membentuk schema strict dari daftar yang sama; `POST /api/v1/attendance/requests` menolak CORRECTION sebelum service. Route keputusan dan repository juga memakai tipe yang didukung saat ini.
- **Model correction baru parsial.** `AttendanceCorrection` mempunyai `attendanceId?`, `attendanceRequestId?` (unique), `requestedByEmployeeId`, `proposedType?`, `proposedServerTime?`, `proposedDeviceTime?`, `proposedStoreId?`, reason, evidence key, status, reviewer, dan waktu review. Model tidak memiliki target `workDate` atau `shiftAssignmentId` tersendiri, idempotency key/fingerprint, policy version, maupun field actor terpisah yang dapat mewakili Admin pembuat sekaligus employee target. `AttendanceRequest` mempunyai rentang `startDate/endDate`, tetapi rentang tidak memilih satu shift.
- **Efek turunan sempit dan belum dipanggil workflow.** `DailyAttendanceRepository.applyApprovedCorrection` menerima correction ID, employee, shift assignment, dan work date. Repository memverifikasi correction tersimpan berstatus APPROVED dan `CHECK_IN`, lalu menghitung PRESENT/LATE dan upsert tepat satu baris `DailyAttendance`. Waktu yang dipakai bernama `proposedServerTime`. Jalur ini tidak menerapkan CHECK_OUT, tidak membentuk request/correction, dan berjalan dalam transaksi terpisah. Guard pending correction di job ABSENT mengenali correction lewat original attendance atau rentang request CORRECTION; tanpa target shift eksplisit rentang itu dapat menahan beberapa shift/tanggal.
- **Closing belum memiliki workflow.** `MonthlyRecap` hanya mempunyai OPEN/CLOSED, agregat, satu `snapshot`, actor/time close, serta unique key `(employeeId, periodStart, storeId)`. Belum ada preview/close/revision/override route atau service. Repository daily status menolak efek koreksi ketika menemukan recap CLOSED, tetapi ini bukan kontrak closing lengkap; uniqueness nullable `storeId` juga perlu dibuktikan di PostgreSQL.
- **Audit bisa append di transaksi repository.** Create/decision request saat ini menulis `transaction.auditLog.create` bersama perubahan request. Migrasi `0001_initial` memasang trigger append-only pada `audit_logs`. `AuditService.record` memakai repository/client sendiri dan tidak menerima transaksi Prisma; memanggilnya dari workflow baru tidak otomatis atomik. Trigger tersebut tidak membuat `Attendance`, `AttendanceAttempt`, correction, daily projection, atau recap immutable.
- **Lock yang ada belum satu protokol.** Attendance attempt, create request karyawan, job ABSENT, dan apply-correction mengambil row lock `employees ... FOR UPDATE`. Decision request yang aktif memakai transaksi Serializable dan compare-and-set status tetapi tidak mengambil employee row lock. Schedule mutation memakai `pg_advisory_xact_lock(hashtextextended(employeeId, 0))`, bukan employee row lock. Closing belum ada. Kesamaan nama “employee lock” tidak membuktikan semua writer saling terserialisasi.
- **Idempotency correction belum tersedia.** Request ID dibuat server, tetapi `AttendanceRequest` tidak menyimpan key/fingerprint retry. Unique `attendanceRequestId` hanya membatasi satu correction per request; ia tidak mencegah POST retry membuat dua request dan tidak menetapkan apakah dua correction berbeda untuk target sama diperbolehkan.
- **API contract menyatakan gap secara eksplisit.** `docs/API.md` menjelaskan CORRECTION tidak didukung. `docs/openapi.yaml` hanya mencantumkan empat `EmployeeRequestType` aktif, skema create generik rentang tanggal, dan routes collection/detail/attachment/decision; tidak ada route correction.
- **Keputusan tanggal yang telah terkunci tetap berlaku.** `workDays` adalah jumlah tanggal kalender unik per employee; dua shift satu tanggal dihitung satu hari kerja. Target koreksi tetap harus memilih shift assignment yang tepat. Tanggal capture offline lintas tanggal adalah kandidat wajib review, bukan timestamp server atau kunci VALID otomatis.

## Strategi transaksi, lock, idempotency, dan audit yang diusulkan

Ini strategi kandidat untuk dinilai setelah kebijakan dipilih, bukan klaim aman sebelum dibuktikan di PostgreSQL.

1. Ambil actor dari session. Mulai transaksi DB; tentukan satu lock protocol lintas writer. Pola row-lock `employees FOR UPDATE` telah digunakan beberapa jalur, tetapi harus disamakan dengan schedule mutation yang sekarang memakai advisory lock dan decision request yang tidak mengambil row lock. Bila target multi-employee dipilih, lock employee ID berurutan stabil; lock recap/assignment mengikuti urutan global yang terdokumentasi.
2. Setelah lock didapat, baca ulang subject, status employee, exact shift assignment, store/historical scope, correction/request state, serta recap status. Validasi kalender H+3 dan policy version memakai timestamp server yang ditetapkan kontrak. Bila waktu diambil dari PostgreSQL setelah menunggu lock, jangan memakai `CURRENT_TIMESTAMP` tanpa mempertimbangkan bahwa nilainya tetap waktu awal transaksi; pilih sumber server-time yang konsisten dan diuji untuk cutoff.
3. Submission: validasi duplicate key/fingerprint terlebih dahulu di bawah lock; jika replay identik, kembalikan hasil tersimpan tanpa correction/audit kedua. Key reuse dengan fingerprint berbeda menghasilkan conflict. Dalam satu transaksi tulis request/correction + audit + notification jika diputuskan. Idempotency tidak menggantikan aturan bisnis terhadap dua key berbeda yang menunjuk target sama.
4. Approval/rejection: scope reviewer sebelum membuka data sensitif; lock target employee, reload state dan assignment; conditionally transisi PENDING satu kali. Jika approved, terapkan projection untuk target tepat dan pastikan closed-period gate di transaksi sama. Simpan reviewer, server decision time, note/reason, serta audit before/after dalam transaction yang sama. Jika ada error pada projection/audit, seluruh perubahan state harus rollback.
5. Jangan update/delete `Attendance` atau `AttendanceAttempt` untuk mengekspresikan correction. Simpan claim/effective provenance di correction dan turunkan status harian dari record yang disetujui. Untuk bukti object-storage, write objek tidak ikut transaksi PostgreSQL: perlu staging/orphan cleanup/compensation dan tidak boleh mengirim key privat ke client/audit.
6. Isolasi Serializable yang dipakai request repo saat ini dapat menghasilkan `P2034`; tetapkan retry policy bounded/idempotent atau conflict yang aman. Employee row-lock saja belum membuktikan aman terhadap schedule advisory lock, close, atau semua route/job. Tambahkan concurrency proof dengan dua koneksi PostgreSQL nyata.

## Langkah aman setelah policy lock

1. Owner menjawab decision matrix; catat pilihan dan tanggal efektif di `docs/DECISIONS.md`/PRD. Jangan mengubah code path sebelum konflik approver, target, time semantics, deadline dan closing tertutup.
2. Bekukan kontrak resource/API dan DTO, termasuk apakah correction memakai request generik atau endpoint terpisah, actor/subject model, evidence rules, idempotency dan error semantics.
3. Siapkan migrasi additive yang dapat direview; cek generated Prisma Client/schema validate dan strategi data lama. Jangan menjalankan migrasi pada database proyek; gunakan hanya database PostgreSQL disposable/CI.
4. Implementasikan service/repository/routes dengan transaction-scoped audit dan shared lock protocol, lalu uji unit/service/route dan strict OpenAPI parity. Integrasikan status projection dan guards tanpa menulis raw attendance.
