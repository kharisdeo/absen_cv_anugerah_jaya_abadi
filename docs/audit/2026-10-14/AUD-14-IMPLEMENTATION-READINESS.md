# AUD-14 — Readiness kebijakan request dan snapshot scope

**Status:** artefak analisis lokal selesai; implementasi production gated menunggu keputusan owner.  
**Tanggal pemeriksaan:** 15 Oktober 2026 (Asia/Jakarta).  
**Scope:** request izin/sakit/cuti/lembur, hak approval, overlap antarjenis, atribusi toko/global, scope historis assignment, snapshot/backfill, dan siklus hidup lampiran surat dokter.  
**Perubahan:** hanya dokumen ini. Tidak mengubah README/status/index, production code, schema/migration, database, provider, atau deployment.

## Kesimpulan

Implementasi AUD-14 belum aman dimulai karena beberapa pilihan bisnis menentukan siapa yang dapat memutus request, apa yang dimaksud request bertumpang tindih, bagaimana request multi-store/global diotorisasi, serta apakah keputusan memakai scope historis atau assignment saat ini. PRD memuat konflik khusus approval lembur. Implementasi sekarang memilih perilaku fail-closed tertentu, tetapi TODO dan AUD-10 tetap meminta keputusan owner; perilaku yang ada tidak boleh dipromosikan menjadi keputusan produk.

Bagian yang dapat dipastikan secara teknis: employee adalah sumber identitas submitter; request saat ini memiliki rentang tanggal dan jenis, bukan target shift/toko; Supervisor scope berasal dari relasi toko terkini dan derivasi jadwal employee; detail dan signed URL diperiksa lewat repository; create/decision menggabungkan mutasi, audit, dan notifikasi pada transaksi database; upload objek lampiran berada di luar transaksi database; test repository yang ditinjau memakai mock dan bukan bukti concurrency PostgreSQL.

### Konflik dan batas fakta

1. Approval overtime: PRD role table/FR-28 mengatakan Supervisor dapat menyetujui lembur, tetapi FR-30 membatasi perhitungan ke approval Admin. Current backend menolak keputusan overtime Supervisor dan report menghitung hanya approver Admin. Ini perilaku yang menjaga perhitungan fail-closed; bukan keputusan bahwa Admin satu-satunya approver final.
2. Overlap: current repository menolak setiap rentang tanggal yang overlap dengan request aktif mana pun, termasuk antarjenis; TODO menyebut ini kebijakan konservatif dan meminta konfirmasi bila overtime boleh berdampingan dengan izin/cuti. PRD tidak menetapkan matriks overlap atau definisi temporal overtime.
3. Scope: request tidak mempunyai toko/shift eksplisit. Resolver current state mengharuskan satu store unik untuk Supervisor. Global, tidak ada assignment, dan multi-store lintas rentang diarahkan ke Admin/tidak muncul di queue Supervisor. Ini bukan keputusan apakah request global/multi-store harus dibagi atau boleh direview sebagian.
4. Histori: shift assignment punya effective dates tetapi bukan immutable versions; EmployeeStore dan SupervisorStoreAssignment adalah relasi saat ini. Request tidak menyimpan scope saat diajukan. Perubahan membership/assignment dapat mengubah hasil access derivation; tidak boleh diasumsikan current relation setara bukti historis.
5. Surat dokter: isolasi prefix dan signed URL singkat sudah ada, tetapi belum ada retention/deletion/legal-hold schedule maupun lifecycle provider yang ditetapkan. TODO selfie retention tidak boleh dipakai sebagai nilai default untuk dokumen medis.

## Strategi snapshot dan backfill yang aman

1. **Policy freeze sebelum DDL.** Owner memutuskan definisi target, store attribution, supervisor authorization, temporal cutoff, overtime approval, overlap, dan retention; perbarui PRD/DECISIONS/OpenAPI dan fixture acceptance. Tidak ada migration yang mengasumsikan global/null berarti toko tertentu.
2. **Inventarisasi read-only.** Pada database disposable/staging yang diotorisasi, hitung request per type/status/date span, jumlah yang berkaitan dengan nol/satu/banyak shift store, global assignment, assignment inactive/changed, membership yang hilang, lampiran tanpa request, dan approval role yang tidak dapat dibuktikan. Output hanya counts/opaque IDs; tidak mengekspor reason atau lampiran medis.
3. **Expand additive.** Tambah kolom nullable dan/atau tabel snapshot child dengan FK yang tepat, source assignment IDs, per-date target scope, createdAt server, snapshot schema/policy version, dan explicit resolution state. Hindari default yang menyulap row lama menjadi “verified”. Simpan request asli dan audit lama.
4. **Backfill deterministik terbatas.** Backfill hanya kasus yang dapat dibuktikan dari sumber historis yang memang immutable. ShiftAssignment effectiveFrom/To bisa menjadi kandidat, tetapi bukan bukti final jika row pernah diedit/direvisi; EmployeeStore dan SupervisorStoreAssignment yang sekarang tidak menyediakan interval historis. Jangan memakai assignment terkini untuk mengarang assignment masa lalu. Ambiguity tetap unresolved/Admin-only sesuai keputusan owner.
5. **Shadow compare.** Jalankan resolver lama dan baru read-only pada fixtures sintetis serta snapshot counts terkontrol; daftar mismatch by reason, tanpa membuat attachment URL. Owner/business reviewer menerima disposition tiap kelas ambiguity.
6. **Dual-read/write rollout.** Setelah migration additive dan review, penulisan baru menyimpan snapshot dalam transaksi yang sama dengan request/audit. Pembacaan baru boleh memakai snapshot hanya untuk row bertanda valid; row legacy unresolved tetap pada guard aman yang disetujui. Pantau mismatch sebelum mematikan resolver lama.
7. **Tighten setelah reconciliation.** Tambahkan constraints/index dan kewajiban snapshot hanya setelah data quality report menunjukkan tiap row punya disposition. Jika rollback, pertahankan snapshot baru dan audit; turunkan pembacaan ke mode kompatibel, bukan menghapus histori atau object.
8. **Purge medical attachment terpisah.** Jalankan dry-run per policy/version dan state; klaim deletion secara bounded/idempotent, hapus object private, baru update pointer/tombstone setelah hasil object-store diketahui. Kegagalan mempertahankan retry metadata. Berikan legal-hold exclusion dan bukti purge; jangan menghapus data selfie atau request rows sebagai side effect.

Skema persis belum dipilih. Alternatif yang dapat dibandingkan saat implementasi adalah child rows per request-target-date/assignment (mendukung multi-store dan constraint relasional) atau satu manifest snapshot immutable dengan schema version (lebih sedikit join tetapi perlu validasi JSON, indeks, dan backfill discipline). Bentuk terpilih harus mempertahankan target per shift bila satu tanggal memiliki beberapa shift; jangan gunakan tanggal request saja untuk memilih satu shift.

## Authorization, IDOR, dan privasi

- Principal session adalah satu-satunya sumber employeeId/actor role. Abaikan/reject employeeId, storeId, approverId, status, scope snapshot, atau role yang dikirim client. UUID request bukan bukti hak akses.
- Terapkan scope di query/repository server sebelum mengambil reason, nama employee, decision note, attachment object key, atau lampiran URL. Pertahankan denial yang tidak membedakan ID random dan ID lintas toko bila policy memilih concealment. Jangan menandatangani URL sebelum ownership/scope authorization selesai.
- Employee hanya boleh membaca request miliknya berdasarkan principal.employeeId yang terikat account; employee tanpa profile fail closed. Admin global sesuai policy role. Supervisor harus memiliki assignment yang sah menurut aturan temporal owner dan request target store yang immutable/valid; jangan menerima toko dari filter/body sebagai izin.
- Recheck role, assignment scope, request status, dan target dalam transaksi approval. Jika scope/revocation berubah bersamaan dengan decision, hasil harus satu serial order yang konsisten; tidak boleh ada race antara query izin dan update.
- Snapshot business location dan actor authorization adalah dua hal berbeda: snapshot menentukan store/shift peristiwa; apakah actor harus masih ditugaskan sekarang adalah keputusan owner. Menyimpan snapshot tidak dengan sendirinya memberi akses permanen ke Supervisor lama.
- List/detail/decision/attachment API hanya mengembalikan DTO allowlisted. Jangan pernah membocorkan object key, bytes, signed URL ke audit/log/notification; URL hanya dibuat setelah auth, short-lived, no-store dan attachment disposition. Pertimbangkan bahwa signed URL tetap dapat dipakai hingga expiry setelah assignment dicabut; owner/security harus menerima residual TTL atau proxy download.
- Alasan sakit dan dokumen surat dokter adalah data sensitif. Minimalkan field/projection pada review, hindari body logging/analytics, gunakan bucket private, akses least-privilege, encryption/provider policy, redacted audit, dan delete workflow yang teruji. Keamanan prefix saja bukan ACL.

## Transaksi dan locking

### Perilaku yang sudah terlihat

- Create melakukan SELECT employee FOR UPDATE, scope check, overlap query, request insert, audit append, dan notifikasi Admin di transaksi Prisma SERIALIZABLE. Prisma P2034 dipetakan menjadi overlap conflict. Ini desain kode dan mock evidence; belum dibuktikan pada PostgreSQL live.
- Decision memakai transaksi SERIALIZABLE, scope check untuk Supervisor sebelum detail, lalu conditional update status PENDING, audit append, dan notification employee dalam transaksi. Race dua decision diharapkan hanya satu update yang menang; tests memakai mocks.
- SupervisorStoreAssignment create/delete menulis assignment dan audit dalam transaksi serializable. Delete menghapus current row sehingga tidak menyediakan query histori assignment.
- Upload doctor note terjadi sebelum transaksi DB; kompensasi delete saat persist gagal adalah best-effort, sehingga orphan cleanup/retry/reconciliation harus diperhitungkan jika retention/purge ditambahkan.

### Protokol yang perlu ditegaskan setelah policy

1. Semua request create untuk employee yang sama mengambil lock per employee dengan urutan konsisten sebelum mengecek conflict/snapshot, sehingga create bersamaan tidak meloloskan pasangan yang dilarang. Approval, cancel, assignment edit, dan scope snapshot mengikuti urutan lock yang didokumentasikan; retry serialization conflict dibatasi dan tidak mengulang object upload tanpa idempotent intent.
2. Semua pemeriksaan menggunakan tanggal date-only dan semantics interval yang disahkan. Ambil competing rows dalam satu transaksi, periksa status lagi setelah lock, lalu lakukan conditional mutation. Request scope snapshot dan audit success commit bersama request create/approval; notification transactional atau outbox/idempotent behavior harus dinyatakan.
3. Bila Supervisor assignment history dapat berubah, decision memperoleh lock/versi scope yang konsisten dan memvalidasi assignment berdasarkan temporal rule pilihan owner. Untuk mencegah TOCTOU, tidak cukup melakukan lookup assignment di luar transaksi lalu update request.
4. Hindari menganggap SERIALIZABLE sendiri cukup tanpa demonstrasi test concurrency aktual dan error retry contract. Jika memilih advisory/row lock, dokumentasikan key yang stabil dan lock order bersama schedule/request mutations. Tidak menambah broad lock yang serializes unrelated employees/stores tanpa pengukuran.
5. Object store dan PostgreSQL bukan satu transaksi atomik. Retention harus memakai durable purge state/claim + retry, dan tidak menghapus pointer sebelum deletion outcome dapat direkonsiliasi. Signed URLs yang telah terbit tidak dapat selalu dicabut oleh DB pointer removal.
6. Audit append success harus atomic dengan state transition, merekam actor/request/entity, policy/snapshot revision dan before/after non-sensitive; jangan mencatat bytes, signed URL, atau object key privat. Denial audit (jika dibutuhkan) tidak boleh membocorkan keberadaan cross-scope entity.

## Acceptance dan verifikasi yang diperlukan

### Unit tests

- Approval matrix per role/type/status, termasuk PRD conflict cases; Supervisor overtime tidak berubah diam-diam dari fail-closed sebelum policy test diperbarui.
- Pairwise overlap matrix untuk semua request types dan status; batas date inclusive/exclusive, same-day, adjacent dates, request duplicate, OVERTIME vs SICK/LEAVE/ANNUAL_LEAVE, cancelled/rejected, dan validasi target shift/waktu sesuai keputusan.
- Scope resolver berdasarkan immutable snapshot: one store, global/null, multiple stores across dates, multiple shifts same date, inactive/ended assignments, employee membership removal, assignment changed after submit, Supervisor reassigned/unassigned, historical unresolved legacy, and current actor authorization vs historical context.
- DTO must not contain employee identity outside permitted view, private object key, attachment bytes, snapshot internals, or live signed URL; approver historical role calculation must be deterministic under role change.
- Doctor-note retention state machine: not eligible/held/eligible, dry-run no writes, duplicate run idempotency, delete success/failure/retry, orphan, pointer clearing, no selfie deletion, and audit redaction.

### API/service/repository tests

- Employee list/detail/create is owner-scoped from session; forged employeeId/storeId/approver/status/snapshot fields are rejected. Profileless employee denies without storage signing.
- Admin global access according to approved policy; Supervisor in-store/out-of-store, global, cross-store multi-range, random UUID, and changed assignment denial/read parity. Test concealment status/body exactly as chosen and ensure no side effect on denied operation.
- Attachment signed URL only after approved scope query; random and forbidden IDs return same safe outcome if concealment is required. Assert exact no-store headers, expiry, disposition, no object key in DTO/log/audit, and no signed URL for missing/deleted/held/purging attachment.
- Request create uploads once, persists snapshot + request + audit + intended notifications; DB failure compensation tested with delete failure and orphan reconciliation. Approval CAS, audit and notification/outbox atomicity verified. Retry/duplicate identity semantics need a policy/contract; current generic request POST has no durable idempotency key.
- API/OpenAPI/FE contract confirms the final request unit, partial vs all-or-nothing review, explicit store/shift targets, and allowed state transitions; no UI trusts a hidden/cached route guard as server auth.

### PostgreSQL isolated concurrency/migration tests

Only disposable CI/test PostgreSQL; never use local project, staging, or production DB for destructive fixture setup. Tests must prove actual blocking/serialization/committed rows, not merely mock calls or transaction options.

1. Two concurrent submissions with conflicting ranges/type pairs for one employee: one commits and one returns the documented conflict; same allowed pair concurrently commits only as policy permits. Repeat for same employee with requests in two stores and global scope.
2. Concurrent requests for different employees do not spuriously conflict or leak scope. Test retries after serialization abort do not duplicate request, attachment object, audit, or notifications.
3. Approval vs cancellation/second decision: one terminal transition, one audit success, one notification; loser has no success side effect. Approval vs Supervisor unassignment/role change and EmployeeStore/ShiftAssignment edit must produce one deterministic authorized ordering.
4. Assignment update after request submission must not alter immutable snapshot target or silently move the request to another Supervisor. An active Supervisor A cannot read/approve target B; null/global and multi-store behavior matches owner-selected policy. Verify an unassigned Supervisor's old signed URL residual is bounded as expected.
5. Migration rehearsal against a copy/synthetic disposable dataset: additive migration, dry-run inventory counts, exact backfill count, unresolved legacy rows remain non-widening, rerun/idempotence, rollback/read compatibility, FK/index/check behavior, and no reason/medical bytes printed.
6. Doctor-note attachment delete concurrent with read-url issuance, request status change, legal hold, and retry: no object is deleted while a protected hold applies; no new URL after purge eligibility/pointer removal; a delete failure remains durable and retryable; audit/event metadata stays minimal.
7. Exercise null store/global semantics and date ranges at PostgreSQL level, including any exclusion/partial unique constraints selected. Confirm actual query plan/indexes and transaction isolation; no assumption that Prisma mock shape equals SQL behavior.
