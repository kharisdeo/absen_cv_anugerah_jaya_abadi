# AUD-12 — Readiness UI koreksi dan parity laporan

**Status:** implementasi UI/backend/report gated; analisis readiness lokal selesai.  
**Tanggal analisis:** 15 Oktober 2026 (Asia/Jakarta).  
**Batas task:** hanya artefak analisis ini. Tidak mengubah source, test, API/OpenAPI, schema, migrasi, backlog lain, atau database.

## Kesimpulan

AUD-12 belum dapat diimplementasikan dengan benar: alur correction backend AUD-11 belum dibuat dan masih menunggu owner memilih policy AUD-10. Analisis frontend serta report dapat diselesaikan sekarang tanpa mengaktifkan submission/approval, menetapkan DTO, atau menebak arti koreksi. Status implementation-gated bukan penghalang untuk artefak lokal ini.

Ada tiga fakta teknis yang menjadi perhatian utama untuk implementasi setelah gate terbuka:

1. Frontend sudah punya checkout dan halaman pengajuan, tetapi tidak ada correction form/review yang berfungsi. Teks checkout yang menyuruh karyawan mengajukan koreksi sekarang menunjuk ke workflow yang belum tersedia.
2. Dashboard membangun status dari satu SQL CTE yang mempunyai cabang `ignoreCorrections`; jalur monthly report secara eksplisit meminta `ignoreCorrections: true`. Jadi status correction pada projection harian dapat dipakai dashboard tetapi diabaikan laporan. Ini bukan parity correction end-to-end.
3. Aggregator monthly report yang sama sudah dipakai JSON dan XLSX, namun kontrak keluaran saat ini tidak membawa provenance correction/original. Parity serializer yang ada tidak dengan sendirinya menjamin sumber/status koreksi yang benar.

## Batas kebijakan dan dependency yang belum terpenuhi

### Gate owner AUD-10

`AUD-10-DESIGN.md` berstatus proposal. Owner belum memilih kebijakan final untuk hal-hal berikut, sehingga readiness ini tidak menetapkan pilihan:

- Approver akhir: PRD role matrix menyebut Admin/Supervisor, sementara PRD batas SLA dan TODO/backend readiness menyebut Admin. Belum diputuskan apakah Supervisor memberi keputusan final atau rekomendasi; scope historis toko serta larangan/izin self-approval juga belum final.
- H+3: belum ada pilihan H0, kalender kerja yang mengikat, sumber hari libur, cutoff WIB, serta versi kalender/policy yang menentukan batas submission.
- SLA keputusan dua hari kerja: belum ditetapkan kalender, saat mulai hitung, atau mekanisme eskalasi. Keterlambatan tidak boleh dianggap approval/rejection otomatis.
- Target correction: harus diputuskan apakah satu pengajuan memilih satu tanggal dan shift, bagaimana CHECK_IN/CHECK_OUT dan multi-shift satu tanggal diperlakukan, bukti yang wajib, dan bagaimana no-original diproses. Keputusan `workDays` yang sudah ada adalah tanggal kalender unik per karyawan; itu tidak memilih shift correction.
- Monthly closing: tanggal 3/cutoff, close lebih awal/terlambat, scope perusahaan vs toko, item pending yang memblokir, force-close-with-exceptions, tindakan atas correction yang baru diputus setelah close, Admin override, second-person approval, reopen/revision, dan default versi report historis belum disepakati.

AUD-10 memberi rekomendasi untuk ditinjau—bukan izin implementasi. Tampilan owner/scope/SLA atau closed period harus menampilkan data kontrak server setelah policy dan backend menyediakannya; jangan menghitung deadline atau memberi kesan suatu keputusan telah disahkan di browser.

### Dependency AUD-11

`AUD-11-IMPLEMENTATION-READINESS.md` menyatakan backend correction masih gated. Route/service correction aktif belum ada; `RequestType.CORRECTION` ditolak oleh jalur request aktif; model `AttendanceCorrection` belum mengikat target shift dan work date secara eksplisit; serta tidak ada kontrak submission, decision, provenance efektif, dan closed-period result untuk UI.

Sebelum UI dikodekan, AUD-11 harus selesai berdasarkan policy owner dan menyediakan kontrak yang disepakati untuk sekurangnya: identitas correction/target, claim time versus server receipt/decision time, reason/evidence, status dan decision result, actor/scope, duplicate/replay behavior, SLA/deadline jika ditampilkan, closed-period outcome, serta referensi raw/original. Bentuk DTO, route, status tambahan, dan error code adalah dependency untuk ditentukan pada backend/API task, bukan keputusan AUD-12 ini.

## Peta frontend saat ini

### Route, submission, dan checkout

- `apps/web/src/app/App.tsx`, `role-navigation.ts`, dan `RolePage.tsx` menegakkan halaman berdasarkan role. Employee memiliki `/employee`, `/employee/history`, `/employee/schedule`, `/employee/leave`, `/employee/requests`, dan notifications. Admin/Supervisor memiliki halaman pengajuan tim; Admin/Supervisor juga memiliki laporan. Belum ada route correction terpisah.
- `apps/web/src/pages/RoleHome.tsx` menampilkan tombol Absen Masuk/Pulang dan shortcut “Pengajuan saya”. `apps/web/src/api/error-message.ts` memetakan `ATTENDANCE_CHECKOUT_WINDOW_EXPIRED` ke instruksi mengajukan koreksi kepada Admin. `AttendanceReceiptNotice.tsx` juga memberi instruksi menghubungi Admin untuk absensi ditolak. Namun route/form correction belum tersedia, jadi arahan ini berakhir sebagai kontak manual, bukan alur yang dapat dituntaskan di website.
- PRD FR-12 mensyaratkan check-out hanya setelah check-in pada hari/shift yang sama; bila check-in terlupa, arahkan ke koreksi. Rencana UI selanjutnya harus mempertahankan konteks check-out gagal/shift target saat membawa karyawan ke correction flow, hanya jika backend mengembalikan target yang aman dan kontrak correction mengizinkannya. Jangan membuat checkout menjadi correction atau menulis ulang percobaan absensi.
- `EmployeeRequestsPage.tsx` menampilkan alert “Koreksi absensi — Belum tersedia”, dan form/list yang berfungsi hanya untuk izin, sakit, cuti tahunan, serta lembur. `employee-request-form.ts` memiliki sentinel tipe `CORRECTION`, tetapi opsi form tidak menampilkannya, validasi menolak tipe di luar opsi, dan serializer tidak menghasilkan correction payload. `attendance-requests-api.ts` mendefinisikan union input/DTO dan daftar tipe aktif untuk empat request tersebut; payload generik memilih rentang tanggal, bukan shift assignment.
- `RequestReviewPage.tsx` dan `attendance-review-api.ts` menangani request yang tersedia sekarang. Label dan keputusan yang dirender mencakup empat jenis aktif; aturan Supervisor mengecualikan keputusan final overtime. Tidak ada panel correction yang membawa target shift, sumber raw, SLA correction, atau closed-period state.
- `EmployeeHistoryPage.tsx`, `EmployeeLeavePage.tsx`, dashboard hooks/client (`use-employee-dashboard.ts`, `use-admin-dashboard.ts`, `employee-dashboard-api.ts`, `admin-dashboard-api.ts`) adalah titik integrasi yang perlu dipertimbangkan untuk link koreksi kontekstual dan status/provenance. Saat ini tidak ada correction action yang dapat dikirim dari riwayat. Data riwayat pribadi tetap server-scoped; UI tidak boleh menerima employee/store authority dari URL atau body sebagai pengganti authorization server.

### Report UI dan kontrak browser

- `MonthlyReportPage.tsx` dipakai oleh route Admin dan Supervisor. Ia memuat filter periode, toko, karyawan, tabel ringkasan/detail, serta ekspor. `monthly-report-model.ts` memformat status dan waktu; `monthly-report.css` menata tampilan.
- `monthly-report-api.ts` menerima month dan filter toko/karyawan, memvalidasi bentuk JSON/XLSX, status harian, summary, detail per shift, dan definisi perhitungan. `DailyReportDetail` saat ini hanya memuat waktu masuk/pulang, durasi, status, store/shift, dan status validasi; tidak ada field sumber correction/original, actor/decision, atau revision. Enum status laporan juga tidak menyatakan status “hasil correction” atau provenance. AUD-12 tidak menambah nama field/status baru sebelum kontrak backend diputuskan.
- UI perlu menyampaikan hasil server secara konsisten, termasuk provenance dan closed/version badge jika kontrak mendukungnya. Jangan menyimpulkan “sudah dikoreksi”, “terlambat”, atau “hadir” dari request PENDING atau dari waktu yang diklaim karyawan.

## Backend report/dashboard saat ini

- `apps/api/src/routes/dashboard.ts` meneruskan principal server ke `DashboardService`; `apps/api/src/modules/dashboard/index.ts` memvalidasi role/filter; `apps/api/src/modules/dashboard/prisma-repository.ts` membangun status shift melalui `statusRowsCte` dan menyusun summary, trend, not-checked-in, ranking, serta dashboard employee.
- `statusRowsCte` menggabungkan schedule, raw `attendances`, request aktif, holiday, dan `daily_attendance_statuses`. Ia memiliki parameter `ignoreCorrections`: jika false, projection dengan `corrected_by_attendance_correction_id` dapat memberi status pada branch daily; cabang lainnya menghindari status projection yang terkait correction. Tidak ada resolver domain tunggal yang mengembalikan hasil efektif beserta jejak correction/original untuk seluruh consumer.
- `apps/api/src/routes/reports.ts` menyediakan `GET /api/v1/reports/monthly` dan `/export`, menggunakan auth principal, filter strict, dan `no-store`. `apps/api/src/modules/report/prisma-repository.ts` memanggil CTE dashboard dengan `ignoreCorrections: true`, menambahkan approved overtime, lalu mengembalikan baris shift.
- `apps/api/src/modules/report/index.ts` mengagregasi baris repository menjadi summary dan daily details; `MonthlyReportService.monthlyReport` mengembalikan JSON. `exportMonthlyReport` memakai hasil agregator yang sama dan mengirimkannya ke `buildMonthlyReportWorkbook` di `xlsx.ts`. Ini memberi fondasi parity JSON/XLSX untuk output yang sudah ada, bukan sumber koreksi yang sama dengan dashboard.
- Model `AttendanceCorrection` dan `DailyAttendance.correctedByAttendanceCorrectionId` sudah ada, dan daily repository memiliki jalur sempit untuk correction CHECK_IN yang disetujui. Itu bukan workflow lengkap atau kontrak source efektif: original raw harus tetap immutable; correction tanpa original tidak boleh dibuat seolah-olah `Attendance`/`AttendanceAttempt` asli.
- Definisi `workDays` yang telah dipilih owner adalah jumlah tanggal kalender unik per karyawan dengan setidaknya satu shift terjadwal yang telah tiba/berjalan dan bukan hari libur; beberapa shift pada tanggal sama tetap satu workday. Detail report tetap satu baris per shift/tanggal. Parity correction tidak boleh mengubah definisi ini.

### Kontrak resolver yang menjadi dependency, bukan DTO pilihan

Setelah AUD-10/AUD-11 disetujui, backend perlu menyediakan satu aturan resolver server-side untuk menentukan nilai efektif per target shift/tanggal dari raw attendance dan correction yang memenuhi policy. Resolver itu harus dipakai dashboard, monthly JSON, XLSX melalui data report yang sama, dan—ketika tersedia—preview/snapshot closing. Consumer tidak boleh menjalankan aturan “correctedBy” sendiri-sendiri atau mengandalkan flag `ignoreCorrections` dengan makna berbeda.

Secara semantik kontrak harus mampu mempertahankan nilai efektif dan asal-usulnya: correction ID/status/decision yang berlaku, original attendance/attempt reference jika ada, serta identitas correction/request bila tidak ada original. Payload, field naming, source enum, precedence multi-correction, aturan CHECK_OUT tanpa CHECK_IN, serta apakah dashboard saat ini menampilkan correction pending atau hanya approved harus ditetapkan oleh policy dan API contract. Raw evidence/timestamp tidak ditimpa; klaim waktu, receipt server, waktu keputusan, dan waktu efektif harus dibedakan sesuai kontrak AUD-11.

Report JSON dan XLSX harus menggunakan satu hasil aggregator/version yang sama. Dashboard perlu mengonsumsi resolved status/sumber yang sama, dengan agregasi yang relevan untuk ringkasan hari ini/trend/ranking. XLSX harus memuat nilai/provenance yang sama seperti layar/API dan tidak menambah perhitungan correction tersendiri. Audit export tetap minimum (filter dan request context), tidak menyalin bukti atau data laporan sensitif ke audit.

## Closed-period behavior yang belum dapat ditampilkan sebagai keputusan

PRD FR-39 menyatakan rekap setelah closing terkunci dan perubahan setelah closing hanya Admin dengan alasan serta audit. Model `MonthlyRecap` saat ini mempunyai OPEN/CLOSED dan snapshot, tetapi workflow preview/close/revision/override/reopen belum tersedia. Guard pada jalur daily status bukan kontrak lengkap untuk semua writer/report.

AUD-10 belum memilih apakah koreksi ke periode CLOSED ditolak, masuk amendment/override dan revision, atau memerlukan reopen; siapa pemohon/approver (termasuk second Admin); apakah revision lama tetap dapat diekspor; bagaimana pending correction/offline diperlakukan; atau kapan cutoff tanggal 3. Karena itu:

- AUD-12 tidak boleh membuat UI yang mengizinkan karyawan/reviewer mengubah periode CLOSED, atau menjanjikan bahwa Admin dapat melakukannya.
- API harus menentukan period state/version dan hasil aksi; browser tidak boleh menentukan CLOSED dari kalender lokal atau mengasumsikan belum adanya recap sebagai periode OPEN.
- Setelah AUD-13 menyediakan kontrak, dashboard/report/export harus menyatakan apakah menampilkan snapshot pada revision tertentu atau hasil terkini. Perilaku ini harus seragam serta terlihat di UI/XLSX. Keputusan histori/default-version tetap gate owner.
- Test harus membuktikan correction yang bersaing dengan closing menghasilkan satu urutan committed yang konsisten, tanpa late write, perubahan snapshot lama, atau koreksi “hilang” dari satu consumer.

## UX, accessibility, error, loading, dan empty-state gate

Setiap state di bawah wajib ditentukan/diuji ketika flow nyata diimplementasikan; state dan pesan yang bergantung pada keputusan harus berasal dari API, bukan asumsi klien.

| Permukaan                 | State minimum yang harus ditangani                                                                                                                                                                                                                                                                                                                                                                          |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Employee correction form  | Loading daftar shift/target; tidak ada target yang eligible atau target ambigu (jelaskan langkah aman tanpa memilih otomatis); invalid date/time/claim/reason/evidence dengan pesan terhubung ke field; submit in-flight mencegah double submit; network timeout/ambiguous response dapat direkonsiliasi lewat idempotent retry; success hanya menyatakan diterima/pending sesuai response, bukan approved. |
| Employee history/requests | Loading/error dengan retry dan empty state; status pending/decision/cancellation hanya mengikuti kontrak; detail menampilkan shift/tanggal dan reference yang diizinkan; correction tanpa original tidak boleh dipresentasikan sebagai raw attendance.                                                                                                                                                      |
| Reviewer queue/detail     | Loading, error/retry, queue kosong, stale/conflict, unauthorized/out-of-scope tanpa kebocoran existence, keputusan sedang dikirim, serta feedback sukses server. Gunakan label/form control nyata dan asosiasi pesan `aria-describedby`/`aria-invalid`; perubahan/asynchronous result diumumkan melalui live region (`role="status"` untuk status, `role="alert"` untuk error); error fokus/field harus dapat dicapai keyboard; semua aksi memiliki nama yang jelas; status tidak bergantung warna saja; tabel responsif dan header dapat dipahami screen reader. Waktu klaim dan server ditampilkan terpisah dan berzona WIB bila contract menyediakannya. Signed URL bukti harus singkat, privat, tidak masuk log/URL browser permanen, dan hanya diminta setelah otorisasi server.

## Acceptance dan security/data-provenance untuk AUD-12 setelah dependency lulus

Acceptance ini mengunci kualitas integrasi, bukan memilih policy atau DTO:

1. Karyawan hanya melihat/mengajukan correction miliknya; direct URL/body tidak dapat mengubah employee, shift, store, role, SLA, atau effective status. Admin/Supervisor hanya melihat/bertindak sesuai keputusan owner dan scope server.
2. Checkout yang ditolak karena check-in hilang/window lewat menyediakan arahan yang dapat diikuti tanpa mengklaim correction telah terkirim. Bila ada navigasi kontekstual, target shift/date/type diverifikasi ulang server; UI tidak mengubah raw attempt/attendance.
3. Submission, retry, keputusan, dan refresh menampilkan state dari record correction yang durable. Request ganda, response hilang, stale decision, atau target sudah berubah tidak menghasilkan success palsu atau duplicate action.
4. Raw `Attendance`/`AttendanceAttempt` dan bukti aslinya tidak ditimpa. Baris efektif tetap memiliki jejak ke correction dan ke original bila ada; no-original correction tetap record correction terpisah. Klaim waktu bukan receipt server dan bukan otomatis bukti valid.
5. Satu resolver efektif dipakai dashboard dan report. Untuk fixture sama, status/detail sumber serta ringkasan yang relevan selaras; JSON dan XLSX berasal dari objek agregasi/version yang sama. `workDays` tetap distinct calendar dates; multi-shift per date tidak menggandakan hari.
6. Scope toko/employee filter diterapkan server-side dan tidak dapat diperluas dari browser. Bukti sensitif tidak tercantum di list/report/export/audit selain metadata/ref yang memang diizinkan; export tetap no-store, audit export minimum, teks XLSX tetap literal, dan tidak ada signed/public URL dalam workbook.
7. CLOSED period, pending correction, approval pasca-cutoff, override, reopen, dan revision mengikuti policy owner/AUD-13 secara eksplisit. Sampai itu dipilih, tidak ada aksi UI yang menyiratkan status/perilaku closed-period tertentu.
8. Unit/DOM/API tests mencakup validasi dan seluruh async/accessibility state. PostgreSQL integration mencakup role/scope, approval/effective source, original immutability, duplicate/concurrency, report parity, dan race terhadap close pada DB disposable. Hasil fake repository atau test serializer saja tidak dinyatakan bukti PostgreSQL.

## Urutan aman

1. Owner meninjau AUD-10 dan mengunci approver/self-approval/scope, target/no-original, H+3/SLA calendar, dan semua rule close/pending/override/reopen. Pertanyaan itu dicatat sebagai dependency; dokumen ini tidak menjawabnya.
2. Selesaikan AUD-11 dengan policy tersebut: server authorization, transaction/audit/lock/idempotency, correction data yang terikat target, result/provenance dan closed-period contract; API/OpenAPI dan PostgreSQL tests harus lulus.
3. Review bersama kontrak UI/report tanpa mengubah semantik: tentukan apa yang dapat ditampilkan serta kesalahan/stale/replay yang mungkin, termasuk source/effective revision.
4. Implementasikan alur employee form dan checkout guidance, lalu reviewer/route gating; validasi local hanya untuk UX dan server tetap otoritatif.
5. Implementasikan shared effective-source resolver di backend dan sambungkan dashboard/monthly JSON/XLSX. Jangan menghapus `ignoreCorrections` sebelum replacement semantics dan regression consumer parity siap.
6. Jalankan targeted unit/DOM/API tests; lalu PostgreSQL disposable untuk scope, source, raw immutability, duplicate/race dan closing gate. Terakhir verifikasi workbook parity/contents dan alur UI end-to-end. Tidak melakukan migrasi pada database proyek, commit, push, atau deploy sebagai bagian readiness ini.

## Gap verifikasi yang masih terbuka

- Tidak ada correction route/form/review end-to-end atau backend correction service yang dapat diuji dari browser saat ini.
- Tidak ada policy AUD-10 yang dipilih owner; AUD-11 belum menyediakan API contract. Karena itu target correction, SLA due date, approver scope, status, duplicate semantics, serta closed-period UI tidak dapat dipastikan.
