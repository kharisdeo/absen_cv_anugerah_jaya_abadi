# AUD-16 — Readiness pengaturan operasional

**Status artefak:** analisis/readiness lokal selesai. **Status perubahan settings baru:** sebagian aman pada CRUD yang sudah ada; policy settings lintas domain masih gated.  
**Tanggal pemeriksaan:** 15 Oktober 2026 (Asia/Jakarta).  
**Batas:** hanya dokumen ini. Tidak mengubah production code, schema/migration, API/OpenAPI, database, provider, deployment, README, atau index. Tidak membaca file `.env` maupun nilai secret.

## Kesimpulan

Belum aman menjadikan seluruh angka/policy dalam PRD/TODO sebagai form Admin yang dapat langsung diubah. Store/radius/akurasi dan master shift/toleransi sudah memiliki source, CRUD Admin, validasi server, UI, dan audit diff. Itu adalah kemampuan master-data yang ada sekarang—bukan bukti bahwa SLA, retensi, validasi alternatif, koreksi/closing, atau saldo cuti sudah memiliki policy version, effective date, atau snapshot yang disetujui.

Scope operasional yang saat ini memang dapat dikelola Admin sebaiknya tetap memakai Store dan WorkShift API yang ada. Perluasan ke settings terpusat, perubahan alasan wajib, atau riwayat efektif harus mengikuti kontrak yang disetujui dan menutup gap audit. Policy yang belum disepakati jangan ditampilkan sebagai editable ataupun diberi default hasil tebakan. Secret dan konfigurasi runtime/provider tidak pernah menjadi field Admin.

`TIMEZONE` bukan policy yang dapat diganti Admin: proses hanya menerima `Asia/Jakarta`. Semua boundary tanggal bisnis/label waktu di UI harus konsisten dengan WIB; timestamp instan disimpan timezone-aware dan disajikan dalam Asia/Jakarta. Tanggal efektif bisnis, bila kelak dipilih untuk suatu policy, harus dinyatakan date-only WIB secara eksplisit; jangan diturunkan dari timezone browser.

## Current bounds, authorization, UI, dan audit

### Store/radius

- Prisma `Store` default radius `10` dan accuracy limit `30`. Route create/PATCH menerima radius dan accuracy sebagai integer positif `1..2,147,483,647`; ini batas representasi PostgreSQL `INTEGER`, bukan batas bisnis/radius aman. Koordinat finite latitude `-90..90`, longitude `-180..180`, maksimal enam desimal. `wifiPublicIp` menerima null atau satu IPv4/IPv6 literal (maksimum 45 karakter). Normalizer/service dan UI memeriksa input juga.
- `GET/POST /api/v1/admin/stores`, `GET/PATCH /api/v1/admin/stores/:storeId`, dan deactivate memakai sesi server, role Admin, no-store, Origin check untuk write, serta sensitive rate limit. Strict Zod body menolak key tak dikenal. Authorization bukan hanya penyembunyian menu.
- UI aktif ada di `/admin/stores` (`AdminStoresPage`/`admin-store-form.ts`). Perubahan koordinat/radius/akurasi/Wi-Fi meminta konfirmasi sebelum PATCH; dialog menampilkan label perubahan, bukan nilai. Ini confirmation, **bukan** field alasan dan bukan effective-date preview.
- Event `store.create`, `store.update`, `store.deactivate` mencatat before/after; audit sanitizer punya allowlist sempit agar koordinat geofence toko boleh tercatat. Repository update selesai sebelum pemanggilan `AuditService.record`; keduanya bukan satu transaksi, sehingga kegagalan audit setelah data berubah dapat memisahkan state dan audit. Schema body/update tidak menerima `reason`, service tidak meneruskannya; event update sekarang menghasilkan `reason: null`.
- Per PRD, perubahan radius memengaruhi **attempt berikutnya**, bukan attendance historis. `AttendanceAttempt.geofenceRadiusMeters` dan `accuracyLimitMeters` menyimpan nilai yang dipakai; store update tidak menulis ulang attempt lama. Ini belum sama dengan scheduled effective date atau histori versi policy yang dapat dipilih ulang.

### WorkShift/tolerance

- WorkShift toleransi default `0`; API menerima integer `0..2,147,483,647` (`breakMinutes` juga non-negatif). `workDays` minimal satu hari ISO 1–7 tanpa duplikasi; validasi jam dan pasangan start/end berlaku. Tidak ada batas bisnis maksimum toleransi, dan tidak ada field tolerance per employee.
- Route Admin `/api/v1/admin/shifts` GET/POST/PATCH/deactivate dilindungi sesi + role Admin; writes cek Origin, `no-store`, sensitive rate limit, dan schema strict. Route PATCH tidak menerima `reason`. `/admin/schedules` mengedit shift; UI menampilkan toleransi dan nilai form dikirim ke API yang sama. Tidak ada effective-date control atau revision history di form shift.
- Event `schedule.shift.create/update/deactivate` memiliki before/after snapshot. `updateShift` memanggil repository update lalu audit service terpisah; bukan satu transaksi. Reason tidak dikirim sehingga `AuditLog.reason` nullable menjadi null. Assignment shift memang date-effective, tetapi itu tidak memberi versioning atas perubahan isi template WorkShift.

### Route reason yang ada — jangan salah menganggapnya alasan settings

- `PATCH /api/v1/admin/stores/:storeId` dan `PATCH /api/v1/admin/shifts/:shiftId`: **tidak menerima** reason; strict schema menolak properti ekstra. Event audit untuk update membawa diff, tetapi reason null.
- `POST /api/v1/admin/system-disruptions`: reason wajib 1–500 karakter dan dicatat sebagai alasan pembuatan record gangguan; ini bukan route pengaturan SLA/retention/validasi.
- `POST /api/v1/attendance/requests`: reason pengajuan wajib dalam body. `POST /api/v1/attendance/requests/:requestId/decision`: `decisionNote` wajib. Ini alasan transaksi request, bukan alasan perubahan policy Admin.
- `POST /api/v1/attendance/verifications/:attendanceId/decision`: schema menerima reason opsional; service menuntut reason non-empty untuk keputusan REJECTED. Ini alasan keputusan verifikasi, bukan settings.
- `GET /api/v1/admin/audit-logs` adalah read-only; Admin tidak dapat mengedit event audit. `AuditService` membatasi reason maksimum 500 karakter dan menyaring key sensitif dari before/after. Trigger PostgreSQL membuat tabel audit append-only, tetapi tidak membuat mutasi Store/WorkShift dan auditnya atomik.

PRD bagian audit mengharuskan pelaku, waktu, before/after dan alasan. Sebagai **proposal kontrak** untuk setting change baru/perubahan sensitif: reason wajib, trimmed, non-empty, maksimum 500, dan audit menyimpan actor server-side, action, entity/scope, before/after yang di-allowlist, version/effective date, timestamp server, request ID, dan reason. Nilai secret/token/credential tidak boleh muncul di DTO, diff, audit, log, error, atau UI. Owner perlu mengonfirmasi apakah alasan wajib berlaku untuk seluruh edit master-data atau khusus perubahan yang mengubah evaluasi/keamanan; perubahan route store/shift saat ini tidak menerimanya.

## Gap effective date, history, dan snapshot

1. Row Store dan WorkShift merepresentasikan nilai terkini; `updatedAt` bukan version history yang cukup untuk memilih policy berdasarkan waktu suatu attendance. Audit timestamp/diff membantu investigasi tetapi tidak menjadi resolver nilai efektif yang dipakai backend.
2. Radius/akurasi adalah pengecualian yang sudah memiliki snapshot pada `AttendanceAttempt`, dan PRD eksplisit bahwa perubahan radius bersifat prospektif. Jangan menyimpulkan aturan prospektif yang sama untuk setiap policy lain.
3. Assignment shift memakai rentang tanggal kalender, tetapi isi WorkShift dapat diperbarui in-place; tidak ada `policyVersionId`/tolerance snapshot pada Attendance/Attempt. Historical recompute, pending evaluation, dan laporan perlu memakai kebijakan yang memang berlaku pada tanggal target, bukan nilai terbaru tanpa keputusan.
4. Retention expiry disimpan per selfie. Belum diputuskan apakah policy baru hanya berlaku untuk objek/attempt baru atau juga menghitung ulang expiry data lama. Satu job menghapus objek private berdasarkan expiry; konfigurasi Admin tanpa provider deletion proof dapat memberi janji privasi yang tidak benar.
5. SLA verifikasi yang ada menggunakan dueAt hasil hitung dari receipt/server time dan konstanta 24 jam, tetapi tidak menyimpan policy version. Correction H+3/SLA, monthly closing, alternative validation, dan leave bahkan belum memiliki lifecycle/versioned policy atau semua flow pemakainya.
6. Untuk correction, offline lintas tanggal, scope historis request, dan closing, perubahan assignment, kalender, atau policy dapat mengubah hasil keputusan. AUD-10..15 mencatatnya sebagai proposal/keputusan produk terbuka; rekomendasi di sana bukan izin untuk mengodekan nilai tertentu.

## Proposed versioned settings contract (rancangan, belum dipilih/diimplementasikan)

Tujuan kontrak: satu sumber versi aktif yang dibaca service backend dan UI, agar tidak ada konstanta berbeda di browser/API atau perubahan diam-diam terhadap histori. Ini bukan persetujuan schema atau pemilihan nilai.

- **Registry/allowlist:** setiap key didefinisikan server dengan tipe, satuan, business scope yang diizinkan (global/store/shift/employee), validasi, klasifikasi (`business-policy`, `security-policy`, `technical-limit`, `deployment-secret`), consumer backend, dan apakah snapshot diperlukan. Key dan scope tidak bebas dibuat dari payload.
- **Immutable version:** conceptual record menyimpan `key`, `scope`, monotonic `version`, typed value, status/lifecycle, `effectiveFrom` yang eksplisit, actor server, `publishedAt`, reason dan referensi audit. Perubahan membuat versi baru; versi terbit tidak diedit/dihapus. Concurrent publish memakai expected-current-version/conditional update agar tidak lost update.
- **Time contract:** tiap key harus menetapkan apakah `effectiveFrom` berupa tanggal bisnis (`YYYY-MM-DD`, kalender Asia/Jakarta) atau instant RFC3339 dengan offset. Instant disimpan timezone-aware/UTC dan ditampilkan WIB; tanggal bisnis tidak di-parse menjadi instant UTC. Batas inklusif/eksklusif serta perlakuan versi yang sudah pending harus ditentukan owner per domain.
- **Resolver tunggal:** service server memilih versi berdasarkan event/business target dan scope yang tervalidasi. UI memanggil read API yang sama untuk nilai efektif, versi, batas/units dan jadwal perubahan; UI bukan evaluator. Semua write/read/no-op/concurrency/unknown-key memiliki kontrak konsisten dan `Cache-Control: no-store` untuk data Admin.
- **Snapshot/provenance:** saat tindakan penting terjadi, simpan pointer ke versi yang dipakai dan snapshot field nilai non-secret yang cukup untuk audit/replay. Jangan mengganti snapshot lama saat publish versi baru. Definisikan snapshot anchor untuk event attendance, submission/decision request, report/closing, serta capture/retention sebelum implementasi domain terkait.
- **Secret/deployment boundary:** secret hanya masuk environment/secret manager dengan masking, rotation, least privilege, dan redeploy/reload policy; tidak ada GET value, PATCH, diff value, atau Admin form untuk credential. Public read API hanya mengembalikan policy values yang memang disetujui dan dibutuhkan client.
- **Migration/compatibility:** bootstrap versi awal harus menggunakan nilai historis yang dapat dibuktikan, bukan mengambil tebakan dari form/browser. Jika source tidak dapat direkonstruksi, jangan mengklaim histori yang persis; catat batas backfill dan pertahankan evidence lama. Cutover harus mencegah dua source authoritative berjalan bersamaan.

Kandidat conceptual entity names (`OperationalPolicyDefinition`, `OperationalPolicyVersion`, `PolicyChangeRequest`) hanya istilah desain. Pemodelan, status draft/approval, scope versioning, date type, revision/rollback, dan policy seed belum disetujui; jangan membuat migration berdasarkan nama/kontrak ini saja.

## Prioritized slices dan gate

1. **P0 — decision record/registry contract.** Owner mengunci kategori yang boleh Admin edit, scope tiap key, siapa yang berhak/approval, effective date basis, snapshot anchor, reason dan concurrency semantics. Ini prasyarat untuk UI/API terpusat. Dapat disiapkan sebagai artefak tanpa mengubah runtime.
2. **P1 — tutup gap pada CRUD yang sudah ada.** Pertahankan Store CRUD/radius prospektif dan Shift CRUD sebagai source saat ini. Sepakati reason wajib/cakupan, lalu tambahkan validated reason, atomic mutation+audit, stale-write protection, audit diff tests, dan browser confirmation. Untuk shift, tentukan date-effective semantics dan bagaimana nilai historis/recompute dipertahankan sebelum mutasi template digunakan untuk masa depan.
3. **P2 — policy service read/publish yang aman.** Setelah P0, buat schema/migration dan API Admin-only berbasis allowlist, immutable version, overlap/duplicate prevention, no-store, reason, audit atomik, concurrency, dan one resolver. UI membaca DTO tersebut; tidak menambahkan nilai policy yang belum disetujui.
4. **P3 — domain-specific rollout, terpisah dan berurutan.** Verifikasi/SLA; offline/drift; correction dan closing setelah AUD-10..14; retention hanya setelah keputusan masa berlaku/expiry lama dan storage+worker provider proof; alternatives hanya setelah owner memilih metode serta trust/provider architecture; leave hanya setelah seluruh AUD-15 decisions. Setiap consumer harus memakai version resolver/snapshot sebelum setting dinyatakan editable.
5. **P4 — deployment/security config.** Documentasikan deployment secret-manager, rotation, validation dan rollout untuk process/provider config. Jangan menyalin rahasia ke database settings, endpoint Admin, browser, audit, atau log.

## Pertanyaan keputusan owner/provider

- Key mana yang editable Admin dan scope-nya (global/per toko/per shift/per karyawan)? Apakah hak Admin tunggal cukup, perlu re-auth/2FA, atau second-admin approval untuk perubahan tertentu? Minimal dua Admin aktif sebagai invariant bukan otomatis approval dua orang.
- Untuk setiap key, effective date adalah business date WIB atau instant server? Boleh dijadwalkan ke depan? Bagaimana menangani request/event yang dibuat sebelum tanggal efektif tetapi diputuskan sesudahnya, event terlambat/offline, dan policy change di tengah periode?
- Snapshot mana yang menjadi source audit/report: nilai saat capture/attempt, saat server menerima, saat submit request, saat keputusan, atau versi yang mengikat seluruh closing? Mana yang dapat di-replay, mana yang hanya provenance?
- Apakah reason wajib untuk semua perubahan store/shift atau hanya geofence/tolerance/security/policy? Apakah alasan harus terlihat ke employee/supervisor, atau hanya audit/Admin? Apakah perubahan perlu preview dampak dan konfirmasi tambahan?
- Untuk shift, apakah toleransi per employee benar-benar diperlukan (FR-26) dan bagaimana override-nya berinteraksi dengan shift template/assignment serta histori? Apa aturan edit `WorkShift` untuk tanggal assignment yang sudah lewat?
- Verifikasi/correction/closing: konfirmasi seluruh ambiguity AUD-10/11/12/13/14 (kalendar hari kerja/holiday, approver, scope, cutoff, pending, override/reopen, late/disruption, snapshot/report parity); jangan pilih nilai hanya karena sudah tercantum di tabel PRD/TODO.
- Retention: owner/legal menetapkan angka, anchor, prospective vs data lama, pengecualian/hold, serta apa yang terjadi ketika expiry dimajukan untuk objek yang sudah tersimpan. Ops/provider membuktikan private storage, delete/retry, job cadence, backlog/alert dan perilaku backup untuk provider yang benar-benar dipakai.
- Alternatives: pilih QR/Wi-Fi/supervisor per scope; setuju TTL aktual dalam rentang PRD, token signing/key rotation dan replay storage, proxy trusted-hop/IP source, supervisor scope/offline fallback, serta provider/network evidence. Menyimpan `wifiPublicIp` saja bukan aktivasi.
- Leave: putuskan LVP-01..14 pada AUD-15 (entitlement, satuan/calendar, period, earned/prorata/carry, reserve/debit, cancel/reversal, negative/exception, scope/version/display) sebelum saldo atau policy UI muncul.
- Infrastruktur: siapa pemilik `DATABASE_URL`, session/storage/notifikasi secrets, bucket/endpoint, app origin, scheduler/provider, proses rotasi dan deployment? Semua tetap di jalur ops, tidak melalui Admin web.

## Acceptance dan rencana test setelah gate dibuka

### Unit

- Typed registry menolak key/scope/value tak dikenal, out-of-bound values, unknown enum, malformed effective date, dan reason invalid; validator API dan client hanya mencerminkan schema authoritative, bukan aturan kedua yang berbeda.
- Version resolver menguji sebelum/pada/sesudah boundary, WIB date-only vs offset timestamp, versi terjadwal, overlap, no-op, expected-version conflict, pending item sesuai policy yang disahkan, serta determinisme saat jam server dimock.
- Audit diff allowlist hanya memuat perubahan policy non-secret dan before/after yang aman; secret sentinel tidak muncul pada DTO/error/log/audit. Versi published immutable; reason/actor/request ID terisi.
- Domain consumer membuktikan update prospektif store tidak mengubah attempt lama; shift/status/report/request menggunakan versi yang diputuskan dan tetap mempertahankan raw attendance immutable.

### API

- Admin dapat read/publish hanya key allowlist dalam scope berwenang; Employee/Supervisor ditolak server-side sebelum repository mutation/read yang tidak perlu. Body strict; alasan/effective date/expected version sesuai kontrak; no-store, CSRF Origin, rate-limit, response/error redaction.
- GET API memberikan versi efektif dan scheduled/history yang aman bagi UI. PATCH tanpa reason, reason kosong, duplicate/stale version, overlap, replay idempotency key, invalid scope, dan concurrent update memperoleh hasil deterministik tanpa kehilangan audit.
- Store/shift endpoints yang sudah ada diuji eksplisit terhadap behavior reason yang sekarang: reason bukan field valid dan tidak tertulis; setelah kontrak baru disepakati, route lama tidak boleh diam-diam melewati policy/audit service baru.
- Endpoint Admin tidak mengembalikan environment/secrets, secret fingerprint/hash yang dapat dipakai, raw provider credentials, maupun deployment variables. Negative test mencoba key/payload rahasia dan memastikan penolakan.

### PostgreSQL terisolasi

- Migration pada DB disposable/fresh; constraints uniqueness dan scope; competing transactions publish policy yang sama/overlap; serialization/retry serta rollback ketika audit insert gagal.
- Assert nilai policy, version pointer, audit event dan idempotency record commit atau rollback bersama. Update stale version menghasilkan conflict, tidak overwrite; trigger/audit role menolak perubahan historis version dan `audit_logs`.
- Change effective date tidak mengubah snapshot attempt/decision/report/close sebelumnya; query resolver deterministik untuk date boundary WIB, multi-store dan null/global scope sesuai keputusan final. Seed/migration tidak menyentuh database proyek/production.
- Retention provider deletion dan worker recovery memerlukan provider test terisolasi; PostgreSQL transaction test saja tidak membuktikan bucket deletion atau scheduler.

### Browser

- Admin melihat nilai/version/effective scope dari API yang sama, preview before/after dan alasan wajib bila diputuskan; confirm/cancel benar-benar mengirim/tidak mengirim request. Nilai lama tetap tampil ketika request gagal/ambigu; stale version meminta reload/rekonsiliasi, tidak mengirim ulang perubahan berbeda.
- UI tidak pernah menampilkan atau menerima secrets. Role guard, keyboard/accessibility, error/loading/empty, store/shift legacy forms, timezone Asia/Jakarta dan date-only boundary diuji dengan interaksi browser; UI test tanpa browser tidak boleh dilaporkan sebagai browser acceptance.
- Domain flow (attendance/review/correction/leave/closing/alternative) membuktikan satu versi rule digunakan end-to-end dan histori lama stabil; ukur hanya setelah masing-masing owner/provider gate selesai.
