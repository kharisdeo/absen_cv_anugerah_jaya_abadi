## Safe execution sequence (not executed)

1. Obtain explicit owner approval for staging account/project, expected recurring and overage cost, region, production separation, named service/incident owners, allowed synthetic data, change window, and whether deployment is in scope. Confirm the `main` branch and exact immutable commit before linking provider resources.
2. Provision/identify staging resources only through the approved account workflow. Use provider encrypted runtime secrets; never put credentials in App Spec, repo, command arguments, shell history, output, or chat. Set the exact HTTPS `APP_ORIGIN`; keep object storage private and separate from public static assets.
3. Confirm network restrictions and TLS for API↔PostgreSQL, API↔object storage, and browser↔app. Verify database identity and `/api/v1/ready` before migrations. Use the database migration runbook and an approved pre-change backup/restore gate; do not use local Compose commands against staging.
4. Verify build, process start, health/liveness, readiness, ingress, SPA deep links, session cookie, role access, and API contract on the exact source commit. Log only commit/version, status codes and sanitized request IDs.
5. Configure and test the backup schedule and retention independently of provider defaults. Capture backup ID/time/region/encryption/access/retention metadata in the restricted evidence store. Ensure evidence contains no credential, signed URL, employee data, or medical content.
6. Restore one selected backup to a distinct isolated target. Before restore, verify target host/project/database identifier and deny if it aliases source/staging/production. Do not restore over a live source. Validate app schema, sample aggregates, audit append-only integrity, attendance/report records, and all database references to private objects without exporting private bytes.
7. Measure RPO and RTO from recorded timestamps. Repeat with a synthetic incident/failure case; a scheduled backup timestamp is not proof that a usable restore meets the objective.
8. Run application smoke and compare normalized report/XLSX output and private-object availability against the chosen recovery point. Reconcile or isolate post-backup writes before an approved cutover; obtain explicit change approval before directing users to the restored target.
9. Test rollback by redeploying the prior immutable application commit only when it is compatible with the already-applied additive schema and new data. If data semantics changed or are incompatible, prefer a reviewed forward fix or isolated recovery plan; do not treat restoring an old backup over active data as an application rollback.
10. Keep the environment out of pilot/production until each row has a sanitized evidence link, timestamp, operator, approver and pass/fail result, and incident/rollback owner has accepted handover.

## Blockers and owners

- Project owner: approve account/project, spend, region, source commit, synthetic test window, operational RPO/RTO target and release scope.
- Platform/DB operator: identify staging resources, private networking/TLS, migration operator, backup provider/settings, offsite location and isolated restore target; prove retention/encryption rather than assuming them.
- Service owner: name incident commander and backup contact, approve alert recipients/escalation, rollback/forward-fix and cutover authority.
- Application/QA: run actual route/build/readiness/browser smoke against staging and verify DB/object reference consistency after isolated restore.
- Production: remains separately undecided. Staging target selection is not approval to deploy production or reuse staging employee evidence.

Until an authorized staging deployment and a witnessed isolated restore meet the measured RPO/RTO and object-reference criteria, AUD-23 is **PARTIAL**. Local template validation or provider documentation is not deployment or recovery evidence.
